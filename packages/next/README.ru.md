# @vetojs/next

Защита для Next.js на базе движка [`@vetojs`](https://github.com/ivan-yuldashev/veto/blob/main/README.ru.md) — **[English](README.md) · [Русский](README.ru.md)**.

Server action в Next.js — это публичная точка входа. Независимо от того, что именно скрыто в вашем интерфейсе, вызвать этот экшен может кто угодно, передав абсолютно любые аргументы.

Из-за этого в каждом экшене разработчикам приходится раз за разом дублировать одну и ту же рутину: сначала определить пользователя, затем загрузить нужный ресурс из базы, проверить права доступа, и лишь после этого выполнять полезную бизнес-логику. Пакет `@vetojs/next` берёт эту работу на себя, позволяя написать всю инфраструктуру проверок ровно один раз.

```sh
npm install @vetojs/next @vetojs/core
```

Библиотека поставляется исключительно в ESM-формате и требует Node.js версии 20 и выше.

## Настройте один раз

```ts
// lib/permissions.ts
import { createGuard } from "@vetojs/next";
import { ac, policyFor } from "./abilities";
import { getActor } from "./auth";

export const withPermission = createGuard({ ac, getActor, policy: policyFor });
```

## Оберните действие

```ts
"use server";

export const updatePost = withPermission(
	{
		action: "update",
		resource: "post",
		load: (formData) => loadPost(formData.get("id")),
		payload: (formData) => ({ title: String(formData.get("title")) }),
	},
	async (ctx, formData) => {
		await db.update(posts).set(ctx.payload).where(eq(posts.id, ctx.row.id));
		revalidatePath("/posts");
	},
);
```

Что происходит под капотом? До того как запустится ваш обработчик, защита уже определит пользователя, соберёт политику, загрузит строку и провалидирует присланные данные. Если хотя бы одна из этих проверок не пройдёт, до бизнес-логики дело просто не дойдёт.

Ваш обработчик первым аргументом получает подготовленный контекст (`ctx`), а следом — все исходные аргументы без изменений:

| Свойство `ctx` | Описание |
| --- | --- |
| `actor` | Текущий пользователь (то, что вернула функция `getActor`). |
| `ability` | Собранный объект ability (на случай, если внутри потребуются дополнительные ручные проверки). |
| `row` | Загруженный ресурс (результат вызова `load`). |
| `payload` | **Строго проверенные** данные — именно их следует записывать в базу, а не сырой ввод пользователя. |

Поскольку все исходные аргументы пробрасываются насквозь в первозданном виде, вам не понадобятся дополнительные переходники для действий под `useActionState` (куда приходят `(previousState, formData)`) или для Route Handlers с их `(request, context)` — всё работает точно так же.

## Умная проверка намерений

В зависимости от того, что именно вы объявили в конфигурации, защита автоматически подстраивает строгость проверок:

| Вы объявили | Что будет проверено |
| --- | --- |
| `load` + `payload` | Разрешено ли писать в эту конкретную строку **и** допустимы ли переданные поля и значения. |
| Только `load` | Разрешено ли вообще выполнить это действие над данной строкой. |
| Только `payload` | Разрешена ли запись в целом **и** допустимы ли эти поля и значения. |
| Ничего | Имеет ли пользователь право выполнить это действие в принципе. |

**Важно:** если функция `load` не вернула строку (например, запись не найдена), вызов будет отклонен. Защита никогда не «съедет» тихо на более слабую проверку без учета строки.

## Обработка отказов

Если проверка не пройдена, летит ошибка `ForbiddenError`. Внутри неё лежат поля `action`, `resource` и точный список нарушений (`violations`), если отказ произошёл на этапе валидации данных.

- Ловите ошибку строго через метод `ForbiddenError.is(error)`.
- **Не используйте `instanceof`** — он вернёт `false`, если в вашем дереве зависимостей случайно окажутся две разные копии пакета `@vetojs/core`.

Для удобства отказы можно обрабатывать централизованно прямо при создании гарда:

```ts
createGuard({
	ac,
	getActor,
	policy: policyFor,
	onDeny: () => notFound(),
	onUnauthenticated: () => redirect("/login"),
});
```

Обратите внимание: ни один из хуков-обработчиков не должен возвращать управление обратно. Этому правилу отлично удовлетворяют вызовы `notFound()`, `redirect()` или обычный `throw`. Если хук всё-таки вернёт управление, защита самостоятельно выбросит исключение — хук нужен, чтобы сообщить об отказе или перенаправить пользователя, но он не может этот отказ отменить.
