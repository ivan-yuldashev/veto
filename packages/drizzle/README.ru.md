# @vetojs/drizzle

SQL-сторона движка [`@vetojs`](https://github.com/ivan-yuldashev/vetojs#readme) — **[English](README.md) · [Русский](README.ru.md)**.

Проверка уже загруженной строки отвечает на вопрос «можно ли этому пользователю трогать *вот это*». Для списка нужно обратное: пусть база вернёт только те строки, которые ему разрешено видеть. Адаптер превращает ту же самую политику в условие `WHERE` для Drizzle.

```sh
npm install @vetojs/drizzle @vetojs/core drizzle-orm
```

Только ESM, Node.js 20 и новее. Пока Postgres.

## Один раз описать таблицы

```ts
import { defineTables } from "@vetojs/drizzle";

const schema = defineTables(ac, { post: posts, user: users, comment: comments });
```

Карта тотальна — забыли ресурс, у которого есть таблица, и код не скомпилируется. Джойны для связей выводятся из внешних ключей, уже объявленных в вашей схеме; писать джойн руками приходится только там, где условие сложнее совпадения ключей.

## Отфильтровать запрос

```ts
const rows = await db.select().from(posts)
	.where(schema.filter(ability, "read", "post"));
```

**Запрос вернёт ровно те строки, которые разрешает `can()`.** Не надмножество, которое придётся перепроверять в JavaScript, и не подмножество, тихо прячущее законные строки. Свои условия дописываются после ресурса — `schema.filter(ability, "read", "post", eq(posts.id, id))` — и сужают выборку вместе с политикой, но не в обход неё. Связи превращаются в подзапросы `EXISTS`, поэтому `author.role` или `comments.some.spam` работают в SQL так же, как в памяти.

Это равенство — весь смысл адаптера, поэтому оно проверено, а не заявлено: сетка на соответствие прогоняет оба пути — `can()` по загруженным строкам и настоящий `SELECT` — на живом Postgres, по строкам с `NULL` в каждой колонке, и требует совпадения множеств идентификаторов.

## Где SQL и JavaScript расходятся

Прямолинейный перевод сломал бы гарантию. `NOT (amount > 1000)` при `amount = NULL` даёт в SQL `UNKNOWN`, и `WHERE` выбрасывает строку, — тогда как движок считает отсутствующее значение разрешимым несовпадением и строку допускает. Запрос с фильтром-запретом спрятал бы строку, на которую у пользователя есть право.

Поэтому каждый листовой предикат компилируется в нечто всегда истинное или ложное — `IS DISTINCT FROM`, `COALESCE(…, FALSE)` и тому подобное, — а значение неподходящего типа решается на месте, а не отдаётся Postgres, который привёл бы `'5000' > 1000` к числам и показал строку, запрещённую движком.

Когда у правила нет честного двузначного перевода — неизвестный адаптеру оператор, квантор помимо `some` / `every` / `none`, отсутствующая колонка — он бросает исключение при сборке запроса. SQL не выполняется, утечь нечему.
