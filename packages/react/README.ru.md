# @vetojs/react

[![Snyk](https://snyk.io/test/npm/@vetojs/react/badge.svg)](https://snyk.io/test/npm/@vetojs/react)

Привязки к React для [`@vetojs`](https://github.com/ivan-yuldashev/vetojs/blob/main/README.ru.md) — **[English](README.md) · [Русский](README.ru.md)**.

Основная идея пакета проста: те же самые правила, которые надёжно защищают ваш сервер, решают, какие элементы интерфейса будут доступны пользователю на клиенте.

```sh
npm install @vetojs/react @vetojs/core
```

Для работы требуется React 18 и новее.

## Создайте строгие привязки один раз

Утилита `createVetoContext(ac)` запоминает вашу схему ресурсов и генерирует набор React-привязок, которые «знают» все ваши ресурсы и их особенности:

```ts
// src/authz.ts
import { createVetoContext } from "@vetojs/react";
import { ac } from "./abilities";

export const { AbilityProvider, useAbility, useCan, useSetRules, Can } =
	createVetoContext(ac);
```

Почему это фабрика, а не обычный импорт? Строго типизированным привязкам необходим ваш объект `ac` (схема доступа). Благодаря этому компонент `<Can>` будет автоматически подсказывать доступные действия для каждого конкретного ресурса и на этапе компиляции не пропустит те, которых не существует.

## На сервере (RSC) контекст не нужен

В серверных компонентах объект `ability` уже находится под рукой, поэтому вам не понадобятся ни провайдер, ни контекст, ни клиентская граница:

```tsx
import { Can } from "@vetojs/react/server";

const ability = await getAbility();

<Can ability={ability} I="update" a="post" this={post} fallback={<ReadOnly />}>
	<EditForm post={post} />
</Can>
```

В серверной версии нет ни директив, ни хуков, ни фабрики — схема ресурсов вычисляется прямо из переданного `ability`. Обе ветки рендера (доступно/запрещено) разрешаются на сервере, поэтому в браузер клиента не отправляется ни строчки лишнего кода.

## Как пользоваться на клиенте

Сначала оберните дерево вашего приложения провайдером один раз, желательно поближе к корню:

```tsx
<AbilityProvider rules={rules}>
	<App />
</AbilityProvider>
```

В проп `rules` передаётся массив правил из `ability.rules` — это ровно те плоские данные, которые прислал сервер. Если на клиенте у вас уже собран объект `ability`, вы можете передать его вместо правил (но передавать их одновременно нельзя).

### Декларативная защита UI

```tsx
<Can I="update" a="post" this={post} fallback={<DisabledButton />}>
	<EditButton />
</Can>
```

Код читается как простая английская фраза: *«Я могу обновить этот конкретный пост»*. Если самой строки данных (например, поста) ещё нет (как в случае с кнопкой «создать»), просто уберите проп `this` — тогда движок проверит, доступно ли действие в принципе.

### Хуки для логики

```tsx
const ability = useAbility();

const visible = postList.filter((post) => ability.can("read", "post", post));
const writable = ability.permittedFields("update", "post", ["title", "status"]);
```

Хук `useAbility` возвращает объект `ability` целиком, открывая доступ ко всем возможным проверкам. Важная деталь: если вызвать его вне `AbilityProvider`, он не станет притворяться, что «всё запрещено», а сразу бросит понятное исключение.

**Оптимизация рендеринга с `useCan`:**

Если вам нужен только ответ «да/нет», используйте хук `useCan` (компонент `<Can>` использует его под капотом). Он точечно подписывается на вердикт и перерисовывает компонент только при его изменении. Например, если у вас выведен список из 50 закрытых строк и меняется вердикт только для одной, `useAbility` заставит перерисоваться все 50 элементов, а `useCan` разбудит ровно одну нужную строку.

```tsx
const canEdit = useCan("update", "post", post);
```

## Смена пользователя без лишних рендеров

Конечно, вы можете передать провайдеру новые `rules` через пропсы, но так как этот проп живёт в состоянии компонента-предка, такая смена вызовет полный ререндер и предка, и всего дерева под ним. Для точечного обновления используйте хук `useSetRules`, который пишет данные напрямую во внутренний стор:

```tsx
const setRules = useSetRules();

const onSwitchActor = async (id: string) => {
	setRules(await fetchRulesFor(id));
};
```

При таком подходе компоненты выше по дереву не перерисовываются, а обновляются только те строки, чей вердикт действительно изменился. Итог: проп `rules` нужен для первичной инициализации правил с сервера, а `useSetRules` — для динамической смены контекста без новых тяжёлых рендеров.

## Спрятать кнопку — не значит защитить данные

Важно помнить: скрытая кнопка в интерфейсе — это просто вежливость по отношению к пользователю (UX), а не реальная защита. Сетевой запрос, который эта кнопка должна была отправить, злоумышленник всё равно сможет отправить вручную. Каждое действие по-прежнему требует обязательной проверки на сервере. Главная ценность `@vetojs/react` в том, что и сервер, и интерфейс читают один и тот же массив правил — это гарантирует, что UI никогда не разойдётся с реальными серверными разрешениями.
