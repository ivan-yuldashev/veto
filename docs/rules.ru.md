# Что такое правило

**[English](rules.md) · [Русский](rules.ru.md)**

Правило — это одна фраза политики: *разрешить (или запретить) такое-то действие над таким-то ресурсом, для таких-то строк, по таким-то полям.* Правила — обычные JSON-объекты, и это главное решение во всём устройстве библиотеки. Их можно сериализовать, отправить с сервера на клиент, положить в базу и править из интерфейса — кодом они не становятся ни на одном шаге.

Политика после этого — просто функция:

```ts
const policyFor = (actor: User): CheckedRules => [
	allow("read", "post", { where: { status: "published" } }),
	allow(["update", "publish"], "post", { where: { authorId: actor.id } }),
	deny("update", "post", { payload: { fields: ["featured"] } }),
];
```

Ни классов, ни билдеров, ни скрытого состояния: чистая функция из пользователя в данные.

## Из чего состоит

```ts
type Rule<T = Record<string, unknown>> = {
	effect: "allow" | "deny";
	action: string | string[];
	resource: string;
	where?: ConditionNode<T>;
	payload?: {
		fields?: (keyof T)[];
		constraints?: FieldConditionNode<Partial<T>>;
	};
};
```

| Поле | Что означает |
|---|---|
| `effect` | `allow` или `deny`. Запрет всегда сильнее — см. [как принимается решение](./rule-evaluation.ru.md) |
| `action` | одно действие, несколько или `"manage"` — сразу все |
| `resource` | о каком ресурсе речь |
| `where` | **какие строки** можно трогать |
| `payload.fields` | **какие поля** можно писать |
| `payload.constraints` | **какие значения** эти поля могут принимать |

## `where` и `payload` отвечают на разные вопросы

Это разделение стоит держать в голове:

- `where` — *можно ли вообще трогать эту строку?* Проверяется по строке, какая она сейчас в базе.
- `payload` — *можно ли записать вот это?* Проверяется по входящим данным.

«Боб может править свои посты» — это `where`. «Боб может править заголовок, но не флаг `featured`» — это `payload.fields`. «Боб может менять статус, но только на `draft`» — это `payload.constraints`. Смешать их — значит получить правило, которое выглядит верным, а защищает не то; разбор сочетаний в разделе [запись](./mutations.ru.md).

## Правила как данные

Раз правило — обычный JSON, оно спокойно переживает дорогу туда и обратно:

```ts
const wire = JSON.stringify(policyFor(actor));
const parsed = parseRules(JSON.parse(wire), ac); // проверка на границе
```

Значения внутри правил остаются JSON-совместимыми: `Date` хранится числом миллисекунд, поэтому в пути ничего не теряется. Что происходит с недоверенным JSON — в разделе [правила извне](./parse.ru.md), а как кодируются значения — в [короткой записи полей](./condition-shorthand.ru.md).

## Почему так устроено

- **`where` и `payload` — разные поля, а не одно общее условие.** Сама структура не позволит написать ограничение по строке там, где имелось в виду ограничение по значению.
- **`payload.constraints` типизирован по частичной форме**, потому что PATCH шлёт только изменяемые поля. Проверяются лишь пришедшие ключи.
- **Тип по умолчанию — `Record<string, unknown>`, а не `any`.** Правила, поднятые из базы, остаются рабочими и не протаскивают `any` в ваш код, а типизированный `Rule<Post>` сужает `where`, `fields` и `constraints` до конкретного ресурса.
- **`"manage"` открыт в будущее.** Он даёт все действия, объявленные у ресурса *на момент проверки*, поэтому действие, добавленное в `defineAbilities` позже, достаётся всем, у кого он уже есть. Обычно это и значит «эта роль владеет ресурсом». Когда разрешение должно быть снимком на сегодня — политика перенесена со списка прав, который выдаёт бэкенд, и новое действие не выдаётся тем, что о нём узнала модель, — перечислите явно:

```ts
allow("manage", "post");            // все действия post, сейчас и потом
allow([...ac.post.actions], "post"); // действия post на сегодня
```

- **`"manage"` — обычная строка, а не особый тип.** Смысл ей придаёт сопоставление правил, поэтому политике, лежащей в JSON, никакого специального кодирования не требуется.
