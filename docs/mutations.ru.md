# Запись — поля и значения

**[English](mutations.md) · [Русский](mutations.ru.md)**

Проверка записи распадается на два вопроса, а не на один:

1. **Можно ли вообще трогать эту строку?** На него отвечает строка, которая уже лежит в базе.
2. **Можно ли записать *вот это*?** На него отвечают входящие данные.

Их важно не смешивать. «Боб может править свои посты» — про строку. «Боб может править заголовок, но не флаг featured» — про поля. «Боб может менять статус, но только на `draft`» — про значения. Одна общая проверка свалила бы все три в кучу.

```ts
if (!ability.canMutate("update", "post", row)) {
	throw new ForbiddenError("update", "post");
}

const result = ability.validatePayload("update", "post", row, data);

if (!result.ok) {
	return badRequest(result.violations);
}

await db.update(posts).set(result.data).where(eq(posts.id, row.id));
```

## `canMutate` — про строку

Решение то же самое, что у `can` с объектом: нашёлся ли подходящий `allow` и не перекрыт ли он запретом. См. [как принимается решение](./rule-evaluation.ru.md).

## `validatePayload` — про данные

```ts
ability.validatePayload(action, resource, row, data);
// → { ok: true, data } | { ok: false, violations: [{ field, reason }] }
```

Метод принимает не только данные, но и **строку** — от неё зависит, какие правила вообще применимы. Правило, действующее лишь на черновики, не должно ограничивать запись в опубликованный пост.

Отказы **явные**: молча ничего не отрезается. Если ключ писать нельзя, вы узнаете, какой именно и почему, — и API ответит настоящей ошибкой вместо того, чтобы сохранить меньше, чем просил пользователь.

Проверяются только ключи, которые реально пришли в `data`, — поэтому PATCH не обязан слать поля, которых не меняет.

### Какие поля

```
разрешено = поля из сработавших allow − поля из сработавших deny
```

Если `allow` не перечисляет поля, он их и не ограничивает: разрешено всё, что не запрещено. Ключ, оказавшийся вне разрешённого набора, попадёт в отчёт как `field not permitted`.

Тот же расчёт, но для интерфейса, делает `permittedFields` — см. [ability](./ability.ru.md).

### Какие значения

Для каждого ключа, прошедшего проверку по полям:

- подходит под ограничение из **deny** → `value denied`;
- у поля есть ограничения из **allow**, и значение не подходит ни под одно → `value not permitted`.

Ограничения из `allow` работают как варианты: достаточно совпасть с любым. Ограничение из `deny` накладывает вето сразу.

```ts
allow("update", "post", {
	where: { authorId: actor.id },
	payload: {
		fields: ["title", "status"],
		constraints: { status: { in: ["draft"] } },
	},
});

// { title: "New title" }      → ok
// { status: "draft" }         → ok
// { status: "published" }     → value not permitted
// { featured: true }          → field not permitted
```

Разница между двумя последними строками принципиальна: `status` Бобу писать можно, просто не в это значение, а `featured` — нельзя вовсе.

## Почему так устроено

- **Одно нарушение на поле.** Ключ, отклонённый на проверке полей, не будет заодно помечен и как проблема со значением: вы получаете первую и самую точную причину.
- **Безусловный `deny` отменяет запись целиком**, даже если данные сами по себе допустимы. Запрет на действие нельзя обойти, прислав только разрешённые поля.
- **Ограничения значений остаются плоскими** — только поля и `and`. «Это значение запрещено» выражается правилом `deny`, а не `or`/`not`, спрятанным внутри ограничения; см. [короткую запись](./condition-shorthand.ru.md).
- **Ограничение на поле, которого нет в данных, не вычисляется** — на этом и держится поведение PATCH.
