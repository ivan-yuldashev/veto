# `@vetojs/drizzle` — та же политика в виде SQL

**[English](drizzle.md) · [Русский](drizzle.ru.md)**

Проверка загруженных строк отвечает на вопрос «можно ли трогать *вот это*». Для списка нужно обратное: пусть база сразу вернёт только то, что пользователю можно видеть. Адаптер превращает политику в `WHERE` для Drizzle.

```ts
import { defineTables } from "@vetojs/drizzle";

const schema = defineTables(ac, { post: posts, user: users, comment: comments });

const rows = await db.select().from(posts)
	.where(schema.filter(ability, "read", "post"));
```

Обещание простое: **запрос вернёт ровно те строки, которые разрешил бы `can()`** — без дофильтровки на JavaScript и без утечек.

```sh
npm install @vetojs/drizzle @vetojs/core drizzle-orm
```

## Настройка

`defineTables(ac, tables, joins?)` сопоставляет каждому ресурсу его таблицу Drizzle. Карта полная: забудете настоящий ресурс — код не скомпилируется.

Соединения для связей **выводятся из ваших внешних ключей**. Если схема объявляет их обычным образом, дописывать ничего не придётся:

```ts
export const posts = pgTable("posts", {
	id: text("id").primaryKey(),
	authorId: text("author_id").references(() => users.id),
});
```

Вывод идёт по кардинальности: у связи «ко многим» внешний ключ лежит на дочерней таблице (`comment.postId → post.id`), у «к одному» — на родительской (`post.authorId → user.id`). Срабатывает он только тогда, когда таблицы связывает ровно один внешний ключ. Ноль или несколько — это неоднозначность, и вы получите громкую ошибку с именами таблиц и просьбой задать соединение явно.

Задать соединение вручную можно всегда — для условий, которые внешним ключом не выразишь:

```ts
const schema = defineTables(ac, tables, {
	post: {
		comments: (post, comment) =>
			sql`${comment.postId} = ${post.id} and not ${comment.deleted}`,
	},
});
```

Соединение задаётся **функцией**, а не готовым выражением: каждому уровню вложенности нужен свой псевдоним таблицы. Именно поэтому правильно собираются и связи на себя (`user.manager`), и длинные пути (`author.manager.role`).

### Два способа вызвать `filter`

```ts
schema.filter(ability, "read", "post");               // ресурс называется один раз
schema.filter("post", ability.where("read", "post")); // условие передаётся явно
```

Оба варианта типизированы: во втором условие привязано к форме ресурса, поэтому передать условие, собранное для другого ресурса, не выйдет — будет ошибка компиляции.

### Ресурсы без таблицы

Ресурс, который существует лишь для того, чтобы закрывать интерфейс — экран аналитики, а не строки, — объявляется явно:

```ts
defineTables(ac, { post: posts, analytics: null });
```

Карта остаётся полной, так что забытая таблица по-прежнему ловится, а «здесь запрашивать нечего» превращается в осознанное заявление. Попытка отфильтровать такой ресурс или дойти до него по связи бросит исключение при сборке запроса.

## Связи превращаются в подзапросы

| Правило | SQL |
|---|---|
| «к одному» или `some` | `EXISTS (SELECT 1 FROM child WHERE join AND condition)` |
| `every` | `NOT EXISTS (… WHERE join AND NOT condition)` |
| `none` | `NOT EXISTS (… WHERE join AND condition)` |

`EXISTS` всегда отвечает истиной или ложью, но никогда `NULL`, — поэтому обернуть группу запретов в `NOT` безопасно.

Аналога `RelationNotLoadedError` здесь нет: в режиме запроса ничего заранее не загружается — в этом и смысл.

## Почему перевод не прямолинейный

SQL и JavaScript по-разному смотрят на отсутствующие и неверно типизированные данные, и дословный перевод тихо ломает гарантию.

Возьмём `NOT (amount > 1000)`, где `amount` равно `NULL`. SQL скажет `UNKNOWN`, и `WHERE` отбросит строку — а движок считает отсутствующее значение определённым несовпадением и строку *разрешает*. Запрос с запретом спрятал бы строку, которую пользователю видеть можно. В зеркальном случае приведение типов (`'5000' > 1000` в Postgres) *показало* бы строку, которую движок запрещает.

Поэтому каждый листовой предикат превращается в выражение, всегда истинное либо ложное и совпадающее с ответом движка:

| Правило | SQL |
|---|---|
| `eq` / `ne` | `IS [NOT] NULL` для значения `null`; обычные `=` / `<>` на колонке `NOT NULL` (чтобы поиск по ключу шёл по индексу); `IS [NOT] DISTINCT FROM` на nullable-колонке |
| `gt` `gte` `lt` `lte`, `contains` | оборачиваются в `COALESCE(…, FALSE)` |
| `in` | `COALESCE(col IN (…), FALSE)`, плюс `OR col IS NULL`, если в списке есть `null`; пустой список → `FALSE` |
| `nin` | отрицание предыдущего |
| `exists` | `IS [NOT] NULL` |
| `has` / `hasAny` / `hasAll` | `&&` и `@>` по колонке-массиву, обёрнутые так, что `NULL` читается как `FALSE`; пустой `hasAll` требует лишь, чтобы колонка была не null |

Значение, тип которого не совпадает с колонкой, решается сразу (`FALSE`, а для `ne` — `TRUE`) и не отдаётся Postgres, который привёл бы его к другому типу.

Когда все листья дают определённый ответ, `and` / `or` / `not` превращаются в обычный булев SQL.

### Когда адаптер отказывается

Для части правил честного двузначного перевода не существует. Тогда адаптер бросает исключение при сборке запроса, вместо того чтобы выдать почти правильный SQL:

- связь без `defineTables` (голый `toDrizzle`);
- колонка, которой нет в таблице;
- не-массив в `in` / `nin` или нескалярное значение;
- оператор, которого адаптер не знает, — каким бы ни было значение. Движок отвечает на него «неизвестно», а `allow` и `deny` читают это по-разному, так что одним предикатом не обойтись;
- квантор «ко многим», отличный от `some` / `every` / `none`. Движок отвечает на него «неизвестно», то есть `allow` не даёт ничего, а `deny` срабатывает, — одним предикатом SQL этого не выразить, и любая догадка показала бы строки, которые движок прячет.

Отказ здесь безопасен по построению — запрос попросту не выполнится. Два последних случая возникают только у правил, протащенных мимо `createRules` и `parseRules`, которые их отклоняют.

## Проверено, а не заявлено

Тесты на соответствие прогоняют оба пути — `can()` по загруженным строкам и настоящий `SELECT` — на наборе, где `NULL` есть в каждой колонке, и сверяют множества идентификаторов. На настоящем Postgres, через PGlite (WebAssembly, без нативной сборки и без запуска сервера).

Набор покрывает все операторы, взаимодействие с запретами, пустые списки `in` и списки с `null`, экранирование в LIKE, поездку `Date` туда-обратно и колонку `customType` с преобразующим кодировщиком.

## Что полезно знать

- **`Date` переживает поездку.** В правилах даты лежат числом миллисекунд, и если целевая колонка — метка времени, число превращается обратно в дату перед подстановкой.
- **`contains` экранирует спецсимволы LIKE** (`%`, `_`, `\`) и ищет буквально, сохраняя чувствительность к регистру, как в движке.
- **Значения подставляются через кодировщик колонки**, ровно как это делают собственные операторы Drizzle, — поэтому колонки `bigint` и `customType` сериализуются одинаково. Единственное намеренное исключение — шаблон для LIKE: это производная строка, а не значение колонки.

## Ограничения

- **Пока только Postgres** — `IS DISTINCT FROM`, операторы для массивов и работа с псевдонимами берутся из `pg-core`. MySQL и SQLite — на очереди.
- **Порядок строк зависит от collation базы**, а для не-ASCII текста он может расходиться со сравнением строк в JavaScript.
