# Серверный рендеринг и статическая ловушка

**[English](ssr.md) · [Русский](ssr.ru.md)**

Правила — обычный JSON, поэтому они переезжают с сервера на клиент тем же способом, каким фреймворк и так возит данные: полезная нагрузка RSC, возврат `load`, пропсы страницы. Nuxt, SvelteKit, Astro, Remix и Next делают здесь одно и то же, и переходник не нужен никому.

```tsx
const ability = buildAbility(ac, policyFor(currentUser));

<AbilityProvider rules={ability.rules}>
	<Toolbar post={post} />
</AbilityProvider>
```

`ability.rules` — тот самый массив, что собрали на сервере. Клиент пересобирает из него ability и задаёт те же вопросы: ни второй политики, ни отдельной ручки за правами.

## Где именно правила пересекают границу

**Next, App Router.** Серверный компонент собирает ability и рендерит провайдер; правила едут в RSC-пейлоаде. Две детали стоят людям вечера: `cookies()` асинхронный, поэтому актора ждут через `await`, а модуль с `createVetoContext` — клиентский: провайдер держит состояние, а состояние живёт на клиенте.

```ts
"use client";

export const { AbilityProvider, useAbility } = createVetoContext(ac);
```

**SvelteKit.** `locals.user` заполняют в `hooks.server.ts`, и прочитать его может только `.server.ts`-загрузчик. Верните правила из `+layout.server.ts` — и они окажутся в `data` у всех дочерних маршрутов:

```ts
export const load = ({ locals }: { locals: { user: { id: string } } }) => ({
	rules: policyFor(locals.user),
});
```

**React Router, бывший Remix.** То же самое файлом дальше: `loader` возвращает правила, `useLoaderData()` читает их в компоненте.

**Nuxt.** Серверная middleware кладёт актора в `event.context`; маршрутная middleware засевает из `useNuxtApp().ssrContext` состояние `useState("rules", …)`, а Nuxt сериализует этот пейлоад для гидратации.

**Astro.** Middleware ставит `Astro.locals.user`, страница читает его и передаёт правила острову пропсами. Пропсы острова обязаны быть сериализуемыми — правила такие и есть, в этом весь смысл.

## Что уезжает, а что нет

**Отправляйте правила.** Они уже сужены до одного пользователя: политика — функция от актора, поэтому в браузер попадает то подмножество, которым он и управляется.

**Не отправляйте то, из чего они получились.** Правила — это интерфейс; сессия, таблица членств и клеймы, породившие их, остаются на сервере.

**Считайте правила видимыми.** Они описывают, что пользователю можно, и знать это ему не вредно, — но пишите их так, будто любопытный откроет и прочитает. Правило, раскрывающее идентификатор воркспейса, которого он иначе не увидел бы, — утечка независимо от того, что показывает интерфейс.

## Статическая ловушка

**У статически сгенерированной страницы нет пользователя.** На момент сборки не залогинен никто, поэтому вердикт, запечённый в HTML, — это вердикт ни о ком, а стоит ему попасть в кэш CDN, как он становится вердиктом обо всех.

Отсюда два честных пути:

**Отрендерить страницу без гейтинга и закрыть после гидратации.** Статическая оболочка показывает то, что видно любому посетителю, клиент забирает правила и раскрывает остальное. Разрыв заметен — мелькнёт незакрытый интерфейс, — поэтому в оболочке держите только по-настоящему публичное.

**Закрывать на краю.** Middleware или edge-функция знает, что у запроса есть пользователь, собирает там ability и делает редирект или подмену. Это снова серверный рендеринг, просто ближе к пользователю.

Чего делать нельзя никогда — запекать правила одного пользователя в страницу, которую получат другие. Если страница кэшируется, кэшируются и правила в ней.

## Сервер всё равно обязан проверить

Спрятать кнопку — это UX. Запрос, который она скрывает, можно отправить руками, поэтому настоящую проверку сервер делает каждый раз:

```ts
if (ability.cannot("update", "post", post)) {
	notFound();
}
```

Это одинаково верно для серверного компонента, `+page.server.ts`, лоадера и обработчика маршрута. См. [гвард](./guard.ru.md) — обёртку, которая делает это один раз на действие, — и [как проверять доступ](./ability.ru.md) про разницу между вопросом со строкой и без неё.

## Почему так устроено

- **Правила — данные, а не объект.** Именно это позволяет им пересечь границу сериализации: экземпляр класса её не переживёт, и вот конкретная причина, по которой библиотека на классах не построена.
- **Один и тот же массив с обеих сторон.** Клиенту не с чем разъезжаться: массив один, собран один раз, прочитан в двух местах.
- **Сборка — на запрос.** Ability — это замыкания над правилами одного пользователя; закэшировать его между запросами значит однажды выдать чужие права.
